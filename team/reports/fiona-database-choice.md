# Database Architecture Verdict: PostgreSQL (Supabase) for Lunaris-Orbit

**Author**: Fiona (Product Manager)  
**Status**: Final Verdict  
**Date**: May 12, 2026

## 1. The Decision

After evaluating the development velocity of **Convex** against the analytical and scale requirements of **PostgreSQL (Supabase)**, my final verdict is to proceed with **PostgreSQL (Supabase)** as the primary data engine for Lunaris-Orbit.

While Convex offers superior initial developer experience for real-time frontend reactivity, the core value proposition of Lunaris-Orbit—training machine learning models on an append-only ledger of trade logic—demands the analytical power and ecosystem compatibility of PostgreSQL.

---

## 2. Rationale

### A. Quant Research & ML Ecosystem (Charlie's Requirement)
The long-term goal is to train an ML model for algorithmic trading. Quantitative researchers (like Charlie) and data scientists operate primarily in SQL and Python (Pandas/Scikit-learn).
- **PostgreSQL**: Industry standard for data science. Seamless export to CSV/Parquet or direct connection via Python drivers.
- **Convex**: Proprietary query engine. Exporting large datasets for ML training would require custom "sync" scripts or high-overhead JSON transformations, creating friction for our Quant team.

### B. High-Fidelity "Append-Only" Ledger
We need to log every trade action *and* the exact market state (RSI, price, spread, volatility) at that moment.
- **TimescaleDB Extension**: Using Supabase/Postgres allows us to enable TimescaleDB, which is purpose-built for time-series data like Forex ticks and OHLCV candles. It handles "append-only" high-volume writes significantly better than a general-purpose document store.

### C. AI Reasoning Storage (`pgvector`)
We intend to log the "AI's reasoning" for every trade.
- **Vector Embeddings**: By using PostgreSQL, we can utilize `pgvector` to store these reasonings as embeddings. This allows us to perform similarity searches later to answer questions like: *"Show me all trades where the AI was 'confident' but we hit a Stop Loss,"* or *"Find market contexts similar to our most profitable trade last week."*

### D. System Integrity & Auditability
In a trading environment, data integrity is non-negotiable.
- **Relational Integrity**: SQL's foreign keys and constraints ensure that every `trade_action` is strictly linked to a `market_snapshot`. This prevents "orphaned" logs that would corrupt our ML training set.

---

## 3. The "Trade-off" (Velocity vs. Power)

We are sacrificing the "out-of-the-box" real-time sync that Convex provides. To compensate:
1. We will use **Supabase Realtime** or **Socket.io** (already in the template) to push live updates to the frontend dashboard.
2. Evan (Frontend) will need to handle state management more explicitly than he would in Convex, but Alice's architecture (ADR-001) for decoupling services via Redis already mitigates the complexity of live data flow.
